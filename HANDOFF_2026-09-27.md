## 7. Pipeline architecture (one screen)

Stage separation: **Stage 1 (retrieval/blocking) owns the recall ceiling; the
matcher + decision rules own precision. Pairs retrieval never surfaces are
unrecoverable by any later stage.**

Flow: `load_sources` (blocking.py) → `HybridIndex.build` (hybrid_blocking.py:
lexical hash index, 11 country-prefixed key types + dense fp16 embedding memmap,
country-segmented, cache under `<model_dir>/cache/<prefix>_dense/`) → RRF-style
`merge_hits` (lexical pool 100 + dense pool 40 → top 60) → `extract_features_for_hits`
(features.py, 33 pair features incl. retrieval scores/ranks) → LightGBM
`predict_proba` → `_predict_with_rules` (tune_decisions.py: per-country
first/additional thresholds + cap) → matching_results.tsv + candidate_pairs.tsv.

Key files in `code/business_entity_resolution/src/`:
- `predict.py` — submission inference; `--decision-rules` loads the JSON (accepts
  full calibration output OR bare rules mapping; country keys lowercased; `*`
  fallback required — enforced).
- `tune_decisions.py` — fresh-slice calibration; wrote
  `models/hybrid_v1/decision_calibration.json`.
- `evaluate_recall.py` — recall@K tables, per-country; `--save` writes JSON.
- `diagnose_misses.py` — miss-bucket breakdown (pool_but_cut / ranked_too_deep /
  hard_miss) + example pairs.
- `diagnose_script_mismatch.py` — cross-script pair counter (new, 2026-09-27).
- `diagnose_output.py` — per-country sanity report on a submission file.
- `hybrid_blocking.py`, `blocking.py`, `preprocess.py`, `features.py`,
  `train_model.py` — the engine. `rerank.py`/`train_cross_encoder.py`/
  `evaluate_rerank.py` — the (abandoned) CE route.
- Repo-root `utils/validate_submission.py` — official format validator.
- `.qoder/repowiki/en/content/` — generated architecture docs (deeper background).
- `Hybrid_retrieval_rebuild_2026-09-26_20-11.md` (repo root, ~45k lines) — the
  full planning log from the hybrid rebuild session.

**Submission format rules** (validator enforces): matching_results.tsv columns
`source1_entity_id`, `matched_entity_ids`; exactly one row per test S1 entity
(1,732,544 rows); empty list = singleton; no duplicate IDs within a list; only
S2/S3 IDs from the test set; every matched ID must also appear in
candidate_pairs.tsv.

## 9. Post-deadline iteration 2 (the real accuracy path, already designed)

The single biggest lever, worth up to ~+7pp recall: **candidate-side transliteration
blocking keys.** Design sketch (agreed with user):
1. Detect Indic-script candidate names (regex over Devanagari/Gurmukhi/Gujarati/
   Bengali/Oriya/Tamil/Telugu/Kannada/Malayalam ranges — see
   `diagnose_script_mismatch.py` for the exact ranges).
2. Romanize each Indic name token into 2–3 variants (phonetic + ISO-style —
   स्टार legitimately becomes `star` OR `shtar` depending on scheme).
3. Index the existing name-key family (name_norm/name_core/name_compact/
   name_sorted/anchors — see `record_key_values` in blocking.py) on the romanized
   forms, candidates only (S1 queries are already Latin; query side unchanged).
4. Re-run evaluate_recall (expect recall toward ~0.93–0.95) → recalibrate via
   tune_decisions → full predict. All local, zero credits.
5. Complement (optional, if credits ever allow): fine-tune the bi-encoder on the
   A100 for the deep Latin-noise tail. CE rerank: stays dead.

Also remember the known tune_decisions quirk: its per-country sweep had a
'US'/'India' vs lowercase case-mismatch bug that was already fixed in
evaluate_rerank.py — if thresholds per country look wrong, check case handling.
